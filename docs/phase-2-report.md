# Phase 2 report: production readiness and real-world validation

Written on 2026-11-15. Covers the work from the Phase 1 MVP (commit `d7eedb0`)
to `main` at `21eac45`, plus the commit that adds this report: 40 commits, six
merged pull requests, about 36,000 lines added across 173 files. Times are UTC.

Updated on 2026-11-16: the Procore duplicate-invoice defect found while writing
this report (issue 12) has been fixed. The statements about it below say so.

## Where it stands

Construction RCM now runs as a hosted service on real infrastructure:
https://construction-rcm.vercel.app, on Vercel, with its records and documents
in a Supabase PostgreSQL database reached over verified TLS. On that
deployment, a billing package was uploaded and read on 2026-11-15, then
reconciled, reviewed, approved and exported, and each step was checked against
the database. Concurrency, recovery, authentication and financial edge cases
are covered by 429 automated tests that run against a real PostgreSQL server.

**It is ready for a supervised pilot, not for unsupervised production use.**
Four things stand between the two:

1. **Reading accuracy on real subcontractor documents has never been measured.**
   Every document read so far was generated by this project. The pilot protocol
   (section 8) makes measuring it part of the pilot, and nothing is paid on the
   reader's output alone meanwhile.
2. **Procore, AI reading and email have never been run against the real
   services.** No credentials exist for them. Each is optional, the product works
   end to end without them, and the interface says when one is not configured.
   A duplicate-invoice defect in the Procore push, found while writing this
   report, has since been fixed and tested against the emulator (issue 12).
3. **Hosting is on free plans.** Vercel Hobby is for non-commercial use, and
   Supabase Free pauses idle projects and does not offer downloadable backups.
   Upgrading is a purchasing decision for the account owner.
4. **Operational safeguards are documented but not yet running.** Nightly
   backups, a tested restore and an uptime monitor are not in place yet.

## 1. What was inspected, and the most significant issues found

Phase 2 started by checking the repository itself instead of the Phase 1
report: re-running the suite and build, and reading the services for missing
organisation filters, writes outside transactions and raw SQL. Then the
reconciliation engine, the job runner, sign-in, email intake and document
reading were reviewed. The Procore integration was checked against Procore's
current official documentation. A separate security review covered the
authentication code. Finally the deployment itself was exercised.

Phase 1's claims mostly held: 208 tests passed. Its own report was candid about
what had not been exercised. PostgreSQL had never been run (only the embedded
database), the Docker image had never been built, and the export check covered
the files and the download route, not the Transfer menu itself.

The issues that mattered most, by customer impact and financial risk:

## 2. What changed, and why

### Data, persistence and recovery

- **PostgreSQL in production** (Supabase), with original documents and exports
  stored in it. One database backup therefore captures everything. Every
  document is content-addressed by SHA-256 and checked against that hash on
  every read.
- **Every change is one transaction under a per-organisation lock**
  (`withOrgLock`, `src/db/tx.ts`). A change happens completely or not at all,
  and two people's changes apply one after the other. Applications carry a
  version that every change increments.
- **A database-backed job queue.** Claims are atomic (`FOR UPDATE SKIP LOCKED`),
  so several servers can share one database. A running job holds a lease
  renewed every 30 seconds; a lease two minutes stale is reclaimed. Failed jobs
  are retried three times with backoff, then shown on the application and under
  System status, and the submitter is notified. A restart resumes the work.
- **Serverless hosting on Vercel.** Work runs right after the request that
  queued it, with a 150-second budget inside the 300-second limit. Anything left
  over is picked up on page views and by a scheduled call. Packages over 4 MB
  are sent in 4 MiB parts, since the host refuses larger requests.
- **Supabase hardening.** Row level security is on every table and the public
  API roles hold no privileges, so the Data API exposes nothing. Migrations are
  applied by Supabase's GitHub integration, and the app only checks the schema.
  Connections are verified against the provider's CA (`DATABASE_CA_CERT`).
- **Visibility.** `/api/health`, which needs no sign-in, reports the database,
  TLS, Data API exposure, storage, queue and runner. Since PR #5 it also opens a
  small test PDF with the same reader uploads use, so a deployment that cannot
  read documents shows as `degraded`. Settings → System status shows the same
  plus failed work and the email-intake log.
- **The pdf.js worker fix** ([PR #2](https://github.com/arsalannkhann/construction-rcm/pull/2)).
  The reader imports the worker itself, so the host packages it. A test
  reproduces the deployed layout without the worker; it failed with the
  production error before the fix.
- **The Docker image** is built from runtime dependencies only, runs as a
  non-root user and has a health check. Migrations take a lock, so instances
  starting together do not apply the same one twice.

### Decisions and review

- Approving, rejecting, submitting and overriding carry the version, and for
  approval the amount, that was on screen. A stale decision is refused and the
  page refreshes.
- A corrected resubmission replaces the earlier one instead of sitting beside
  it. A duplicate application number lists the other submissions.
- Reading a package again keeps the reviewer's corrections while the document
  they were made on is unchanged, and says which ones it dropped.
- A reviewer can remove a file from a package, and the package is read again
  with the original kept and the removal audited
  ([PR #3](https://github.com/arsalannkhann/construction-rcm/pull/3)).

### Financial correctness

All arithmetic is done in our code, in integer cents and basis points. No
printed total and no AI output is used as the result of a calculation.

- **Stepped retainage:** a lower rate past a percent-complete threshold, on
  further work only or on all work, with the threshold moving when change
  orders change the contract sum.
- **Recorded retainage releases.** An approver records a release before it is
  billed, and it cannot exceed what is held. The application that bills it is
  checked against it, and the approval records it.
- **Deductive change orders** are checked in the right direction. A credit
  beyond the deduct, or a deduct billed as a charge, is blocked.
- **Checks on what the reading saw,** blocking approval until a person resolves
  them wherever the amount paid could be affected:
  - the schedule's printed grand total against the integer-cent sum of the rows,
    column by column;
  - gaps in the printed page numbering;
  - pages with no text layer;
  - two application numbers, or two pay applications, in one package;
  - the G702 and the G703 printing different totals.
- **Already covered from Phase 1 and re-tested:**
  - previous billing against the last approved application (re-billing caught);
  - unapproved change orders excluded until approved;
  - lines billed beyond their scheduled value;
  - duplicate and out-of-sequence numbers;
  - a second application for the same period, or a period that does not
    advance;
  - opening balances for contracts already under way;
  - a configurable rounding tolerance;
  - separating "fix a misread" from "adjust what is paid", which is how partial
    approval is recorded.

### Authentication and access

- **Password rule:** at least 10 characters, common passwords refused, and the
  email or name refused.
- **Password reset:** single-use, expiring links; signs the user out
  everywhere; leaves two-step verification on. Where email is not set up, the
  page says so plainly, and owners can issue a link (operators: `pnpm
  reset-password`).
- **Two-step verification:** TOTP (tested against the RFC vectors) with
  single-use recovery codes. Organisations can require it for every member.
- **Sessions:** listed and revocable, with Secure, HttpOnly cookies and only
  the token's hash stored.
- **Throttle:** a database-backed sign-in throttle that holds across restarts
  and servers.
- **Every security-review finding is fixed,** each with a regression test
  written as the attack (`tests/auth-hardening.test.ts`):
  - an invitation into an account with two-step verification joins only after
    the code;
  - admins cannot recover members who belong to another organisation;
  - a browser that has signed in before stays usable while strangers guess;
  - the client address comes from the host's header.
- SSO was evaluated and deliberately left out of the pilot
  ([authentication.md](authentication.md), "Single sign-on").

### Document reading

- The text reader declines what it cannot read reliably instead of guessing:
  - decimal-comma figures;
  - schedule columns it cannot identify by heading;
  - a cover letter that mentions a waiver;
  - a second pay application in the same file.
- It also reports page numbering, the printed grand total, conflicting values
  and unreadable pages, for the checks above. The AI engine reports the same
  facts except unreadable pages, since it reads page images.
- **An evaluation harness:** `pnpm eval:extraction` scores a reader against
  ground truth. The synthetic corpus and real documents are kept strictly
  apart, and the real-document folder is git-ignored. A regression gate runs
  in `pnpm test`.
- Measured on the synthetic corpus, confidently wrong values went from 100 to
  0 ([extraction-evaluation.md](extraction-evaluation.md), section 7). That
  says nothing about real documents.

### Email

- Intake processes each message once, by Message-ID or by content when there
  is none. It checks the sender against the subcontractor's contact and
  domain, and logs every message. An unknown sender's package is blocked from
  approval until someone vouches for it, or is turned away under the strict
  policy.
- Outbound messages are stored before they are sent and deduplicated. Wording
  that implies approval or payment is refused unless the sender vouches for
  it, and that is recorded. Without a provider they are saved as drafts
  labelled "not sent".

### Procore

- The notes were rewritten from the official documentation. Every fact is
  marked verified, with its page, or could not verify
  ([procore-api-notes.md](procore-api-notes.md)).
- **Rate limits:**
  - waits on `X-Rate-Limit-Reset`, measured by Procore's clock;
  - honours `Retry-After` on a 503;
  - retries only reads;
  - never resends a write.
- **Pagination** builds its own page URLs and refuses a repeated page.
- **Ids** beyond 2^53 are kept exact.
- **Token renewal** happens once at a time across servers, and the new pair is
  stored before it is used. A renewal that gets no answer is not mistaken for a
  lost connection.
- **One invoice per application** (added on 2026-11-16, after this report was
  first written). A push claims the application in the database, so no other
  server can push it at the same time. It lists the subcontract's invoices
  before creating one and refuses when the number is already there. A create
  request that gets no usable answer is recorded as "no answer", not "failed",
  and sending again adopts the invoice that request created instead of making
  a second. Tested against the emulator, including a dropped connection, a 502,
  an answer without an id and a server that stopped mid-push.
- [procore-validation.md](procore-validation.md) is the exact sandbox
  procedure, added with this report.

### Lien waivers

Not changed in Phase 2. The Phase 1 pre-screen already did what the brief asks:

- It checks completeness (present, signed, amount, date) and consistency with
  the application.
- It recognises Texas, California and Florida statutory form wording, citing
  the statute (`src/server/compliance/jurisdictions.ts`).
- It never states that a waiver is valid. Non-statutory wording, listed
  exceptions, another state's form and an undeterminable type are marked
  "needs qualified review", which only a controller or admin can sign off.

No construction-lien attorney has reviewed the rules.

### Product experience

- **Sign-in screens:** a second step, forgot password and reset password,
  each with plain explanations.
- **Profile and policy:** two-step setup and signed-in devices; the policy to
  require it.
- **System status:** failed work with retry, and the email-intake log.
- **Contracts:** stepped retainage terms and a releases panel.
- **Review screen:**
  - stale-decision refresh;
  - other submissions with the same number, and replacement;
  - a warning as you type when a message implies payment;
  - the remove-a-file control.
- **Integrations:** a page that says exactly what Procore does and does not do,
  and how far it has been tested.
- **Unconfigured services** are labelled as such everywhere.

  not verified.
- [operations.md](operations.md): deploying, backups, restore, failures,
  monitoring and onboarding.

  [procore-api-notes.md](procore-api-notes.md) and [procore-validation.md](procore-validation.md).

## 8. Deploying and onboarding the first pilot customer

The deployment exists. For a fresh environment, follow `operations.md`
("Use Supabase as the database", "Deploy on Vercel"). These are the steps from
where things stand.

### A. Decisions only the owner can make

1. Upgrade the Vercel team to **Pro**, and the Supabase organisation to a
   **paid plan**. Consider point-in-time recovery there as well.
2. Whether to add an **Anthropic API key**, so scans and photos are read.
3. Whether to set up **Resend** (invitations, messages, password-reset email)
   and an **inbound email provider**.
4. **Procore:** leave it unconfigured for the first pilot unless the customer
   needs it. If they do, the sandbox validation
   ([procore-validation.md](procore-validation.md)) comes first.

### B. Before the customer signs in

1. On Vercel Pro, change the schedule in `vercel.json` to `*/5 * * * *`, merge,
   and confirm Vercel → Settings → **Cron Jobs** lists `/api/jobs/run`. Then
   confirm in the logs that a run happened.
2. If the customer will use a custom domain: add it in Vercel, set `APP_URL` to
   it, and redeploy. Invitation and reset links are built from `APP_URL`.
3. **Backups:** schedule a nightly `pg_dump --format=custom` through the
   session pooler to storage off the database host, and keep 30 days. **Restore
   one** into a scratch database, start an instance against it, open an approved
   application, download its PDF and run the audit-chain check (`operations.md`,
   "Backups").
4. **Monitoring:** an uptime check on `https://<domain>/api/health` every
   minute, alerting on HTTP 503 and on `"status":"degraded"` lasting 10 minutes.
5. **Finish the live checks:**
   - turn on two-step verification for the owner account and save its recovery
     codes;
   - invite a second member and sign in as them;
   - reject a test application;
   - record the results in the README.
6. Keep `RCM_SECRET_KEY` and `CRON_SECRET` in the team's secrets manager.
   `RCM_SECRET_KEY` is permanent: a new one breaks everyone's second step.
7. Check `/api/health`: `ok`, `tls: verified`, `exposedTables: 0`,
   `storage: database`, `pdfReader.ok: true`.

The owner's own organisation on the live site holds the sample package used for
these checks. It is invisible to other organisations and does not need to be
removed.

### C. Onboarding, with the customer's controller on a call

These are the steps in `operations.md`, "Onboarding the first customer", in
short:

1. **Organisation and security.** The controller signs up and names the
   organisation. They turn on two-step verification, save the codes, and require
   it for everyone (Settings → Team → Security; it moved there in Phase 3).
2. **Team.** Invite people by role: owner or admin, controller (approves and
   overrides), project accountant (reviews), project manager, viewer. Without
   outbound email, copy each invitation link and send it yourself.
3. **Review policy:** rounding tolerance, required waivers, signature and
   notarisation, the low-confidence threshold, and the unknown-sender policy.
4. **One project first,** with its state, which decides the lien waiver rules.
5. **Subcontractors,** with each billing contact's email address.
6. **Subcontracts:**
   - number, amount and retainage, with stepped terms under **Edit terms**;
   - the schedule of values pasted from the spreadsheet;
   - change orders, approved and pending.
7. **Contracts already being billed:** upload the most recent approved pay
   application first, then **Set opening balances…** from its finding.
8. **The first live package:** upload it, go through every finding with the
   controller, and record every disagreement with what they would have caught
   by hand.

### D. During the pilot

1. **Double-key the first three packages from each subcontractor,** and every
   new form. Two people key each one into a truth file from the PDF without
   looking at the app's reading, and a third settles differences
   (`extraction-evaluation.md`, "Pilot protocol").
2. **Pay nothing on the reader's output alone.** Every blocking finding is
   resolved by a person, and reviewers check figures against the document.
3. **Measure** with `pnpm eval:extraction --set real`. Record the date, commit,
   engine and document count, and report real and synthetic figures
   separately.
4. **Any confidently wrong value stops the line.** Reproduce the layout as a
   synthetic case, fix the reader, raise the gate and measure again.
5. **Reduce double keying** only after at least 30 documents from at least 5
   subcontractors show no confidently wrong value. Even then, keep
   double-keying 1 package in 10.
